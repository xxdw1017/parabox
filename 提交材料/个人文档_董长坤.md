# 《递归之箱》个人文档

**1 人智能编程组 · 完成人：董长坤 · 2026 年 9 月**

> 项目：用 Python + Pygame 复刻《Patrick's Parabox》核心玩法的单关卡游戏——在推箱子之上，把方块变成可以走进去的封闭世界。
> 代码仓库：<https://github.com/xxdw1017/parabox>　·　演示视频与可执行程序见仓库 Releases

---

## 一、共同工作

### 1.1 整体设计目标

- **主目标**：做一个**可完整游玩**的复刻作品——推箱子移动、嵌套世界进出、胜利判定、选关界面四项必做功能全部可用，并用 2 个关卡把核心机制演示清楚。
- **设计原则**（三条，贯穿全程）：
  1. **规则先行**：任何机制先写进 `.dsh/skills/*/SKILL.md` 定稿，再写代码；技能未覆盖的情况先提问，不自行发挥。
  2. **逻辑与表现分离**：纯逻辑层禁止 import pygame，规则可脱离图形库独立测试。
  3. **数据驱动关卡**：新增关卡只加 `levels/*.json`，不改代码。
- **目标达成**：必做 4 / 4 全部达成；选做完成 1 项（撤销 / 重置）；另完成 6 项超出开题预期的机制（嵌套不限层数、双向穿口与吞食、双条件判定点、BFS 解算器、108 个自动化测试、文档一致性校验）。

### 1.2 分工说明（1 人 + AI 智能编程）

| 角色 | 承担的工作 |
|---|---|
| 本人（董长坤） | 需求与机制设计、规则定稿（AGENTS / RULE / 4 份 SKILL）、优先级与取舍、代码审查、观感与手感验收、文档与演示 |
| AI（DSH 智能编程） | 按规格实现代码、补齐单元测试、文档校对、BFS 解算器原型、关卡数据转换与排版脚本 |
| 精力分配 | 机制与文档约 40%，编码约 35%，测试与验证约 25% |

**协作方式**：我定规则与验收标准，AI 在规则内实现并自查；每一次改动都必须跑通全部单元测试，小步提交、全程可回溯。凡是无法自动验证的产出（配色观感、手感），一律保留人工验收环节。

## 二、代码总体框架（含流程图）

![三层架构与数据流](screenshots/framework.png)

- **7 个源码模块 1326 行**，按三层组织，依赖方向严格单向：
  - **驱动层** `main.py` / `game.py`：入口、主循环、场景状态机（选关 / 游玩 / 通关），把按键翻译成"推 / 进 / 出 / 撤销"这类**语义动作**；
  - **表现层** `render.py` / `ui.py`：多层世界绘制、内层缩略图、HUD、选关界面——**只读状态，禁止修改**；
  - **逻辑层** `world.py` / `entity.py` / `logic.py` / `nested.py`：地图与嵌套数据结构、口（door）判定、推箱与箱链、进出与搬运、胜利判定——只依赖标准库。
- **数据流**：键盘事件 → 语义动作 → `logic.move()` 纯函数 → 新状态 → 渲染层只读绘制。状态是**嵌套 dict**（`root` / `player` / `return_stack` / `moves`），层数由关卡数据决定，代码不写死深度。
- **为什么这样切**：规则是评分主体，必须能在没有图形库、没有显示器的环境里被反复验证；表现层只读由断言兜底，AI 改渲染时不可能悄悄改掉规则。

## 六、个人工作：关键代码说明（含流程图）

![一次按键的完整判定流程](screenshots/flow_move.png)

**① 判定优先级（`src/logic.py::move()`）**：一次按键按固定顺序判定六条分支——
出口 → 墙 → 空地 → 整链推动 → 吸入（吞食）→ 进入箱子；全部不满足则状态不变、不记步数、不进撤销栈。

**② 为什么顺序不能换**：站在口格朝外走必须**先于**碰撞判定，否则会被当成撞墙；"整链推不动"必须**先于**"进入箱子"，否则能推动时也会误触发进入。这个顺序在 SKILL.md 里写死，改动前必须先列出受影响的测试用例。

**③ 关键代码（节选自 `logic.py` 与 `nested.py`）**

```python
# 计数只在这一处发生：一次按键 = 一步（曾因搬运路径重复计数导致 37 步记成 39 步）
def _accepted(state, new_state):
    new_state["moves"] = state["moves"] + 1
    return new_state

# 进入落点 = 对侧那条边的中心口格；返回栈记 (world_ref, box_uid)，退出时现查位置
def enter_world(state, box, direction):
    inner = box["inner_world"]
    side = opposite(direction)                       # 从下方进入 → 落在内层底边的口
    cell = side_center(inner, side)
    state["player"] = {"path": state["player"]["path"] + [box["uid"]], "x": cell[0], "y": cell[1]}
    state["return_stack"].append((state["player"]["path"][:-1], box["uid"]))

# 口由内层地图自己决定：内层宽高为奇数，四条边的中心格不是墙就有口
def has_door(world, side):
    x, y = side_center(world, side)
    return not is_wall(world, x, y)
```

**④ 口模型与双向穿口**：内层宽高必须是奇数，四条边的中心格即口位；边缘环上除中心格外必须都是墙，解析期即报错。箱子与玩家共用同一个口与同一个落点——外层推箱时箱链末端的箱子会被推进别人的口（吞食），内层推箱时再推一步就把它推回外层。

## 七、效果和结论

**效果**

- **功能**：2 个关卡可完整通关（最短解 5 步 / 37 步），选关、撤销、重置均可用。
- **质量**：108 个用例全绿（规则 41 / 数据 44 / 渲染 23）；用**没装 pygame** 的解释器执行时 85 个规则与数据用例照常通过、23 个渲染用例自动跳过——分层不只是文档里的约定，而是可复现的事实。
- **可解性**：自研 BFS 解算器搜索 15,191 个状态、调用规则 57,651 次，求出「吞食01」37 步最短解；两关最短解都固化成回归测试，关卡被改坏会立刻报红。

**结论**：核心机制（嵌套进出、吞食、双向穿口、跨层冻结、双条件判定）全部按 SKILL 规格实现并通过测试；剩余差距集中在表现层（音效、计时、动画、死局提示），属于开题时就划为"选做"的范围。后续方向：解算器工具化、动画补间、更多关卡。

## 八、AI 编程感受（含流程图）

![AI 协作流程](screenshots/flow_ai.png)

1. **规则先行，AI 才敢放手写**：把机制先写进 SKILL.md 再让 AI 实现，是本次最有效的做法。规则写清楚后，AI 的产出可直接对照验收；`RULE.md` 还明确要求"技能未覆盖的情况先提问、不自行扩展机制"，避免了机制被悄悄改掉。
2. **把"原则"翻译成"可判定断言"**：AI 看不到画面，也无法判断"好不好看"。于是把观感拆成可执行断言——代码里的每个颜色必须出现在渲染技能文档里、配色对比度必须达标、渲染后状态必须逐字节不变；再由程序生成预览图交给人眼确认。**无法判定的要求等于没提**。
3. **用工具推翻自己的判断**：我曾凭肉眼判定「吞食01」无解，被自己写的 BFS 解算器直接推翻；解算器还给出一个 21 步"隧道解"，暴露出关卡曾被误加了一个底边口——去掉后才是 37 步必吞食解。这件事说明：**"我觉得"不是证据**，可复现的计算才是。
4. **验收与提交必须分开执行**：我曾把"改代码 → 跑测试 → 提交"串成一条命令，测试的退出码被管道吞掉，结果提交了一个不一致的状态，只能用 `git commit --amend` 补正。此后改为分步执行、逐条检查退出码，这条习惯也写进了交付检查。

**一句话总结**：AI 让实现速度提升明显，但它需要三样东西才能可靠工作——**清楚的规格、可自动判定的验收标准、以及一个人来拍板**。这三样正是本次项目投入最多的地方，也是我认为最值得保留的经验。
